# Engmark

Тренажёр английской лексики. Монорепозиторий: Go API в `backend/`, экран занятий на Vite и React в `frontend/`.

## Запуск

- `make dev` поднимает Postgres, затем в одном переднем плане запускает API на `:5050` и экран на `:5173`. Ctrl+C останавливает оба процесса. Postgres продолжает работать. При старте API применяет миграции и, если колода пуста, заливает в неё `data/cards.json`.
- `make env-down` останавливает локальный контейнер Postgres. Файлы базы в `out/pgdata` остаются. Серверный стек этой командой не затрагивается.
- `make run` собирает API и слушает `:5050`.
- `make web` запускает только экран на `:5173`. Админка открывается на http://localhost:5173/admin (см. «Админка: вход»).
- `make test` гоняет тесты Go. Нужен Docker: тесты поднимают свой Postgres и не пользуются базой от `make run`.
- `make test-race` то же с детектором гонок.
- `make host-up` собирает серверный образ и поднимает сайт только из `docker-compose.yaml`. `make host-down` останавливает этот стек и сохраняет том базы. `make host-backup` снимает дамп его базы.
- `make admin-hash` спрашивает пароль админки и печатает строку для `ADMIN_PASSWORD_HASH`. `make export-cards` сохраняет колоду из базы в `data/cards.json`.

## Окружение

Скопируйте пример и заполните локальные значения:

```sh
cp .env.example .env
```

В `.env` задайте `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` для контейнера Postgres. `DATABASE_URL` — тот же аккаунт на опубликованном порту `127.0.0.1:5433`:

```
DATABASE_URL=postgres://engmark:changeme@localhost:5433/engmark?sslmode=disable
```

```sh
make dev
```

`make dev` остаётся на переднем плане. При старте API применяет миграции и, только если у колоды admin `revision = 0`, заливает в неё `data/cards.json` из рабочего каталога процесса. Если ревизия уже не нулевая, файл игнорируется и это пишется в лог. Ctrl+C останавливает API и экран. `make env-down` убирает локальный контейнер Postgres.

API слушает `http://localhost:5050`. Экран ходит в `/api` своего origin. Vite проксирует этот префикс на API, браузер напрямую на `:5050` не ходит.

`docker-compose.yaml` — серверный стек: Postgres, API и Caddy. `docker-compose.override.yaml` на ноутбуке подключается сам: публикует `127.0.0.1:5433` и хранит данные в `out/pgdata`. `make host-up` передаёт `-f docker-compose.yaml` и этот файл пропускает.

Если переменные пула не заданы, действуют значения по умолчанию: `DB_MAX_CONNS=10`, `DB_MIN_CONNS=1`, `DB_MAX_CONN_IDLE_TIME=5m`, `DB_HEALTH_CHECK_PERIOD=30s`. `LOGGER_LEVEL` по умолчанию `info`. `LOGGER_FORMAT` на ноутбуке `console`, в серверном контейнере `json`.

Таймауты HTTP, если их не переопределить: заголовок 5 с, чтение 10 с, запись 15 с, простой 60 с, заголовки до 65536 байт.

## API

- `GET /healthz` отвечает 200 и в базу не ходит. Процесс всё равно проверяет Postgres при старте и не начинает слушать, если проверка не прошла. В JSON может быть поле `version`.
- `GET /readyz` отвечает 200, когда Postgres доступен и каталог уже лежит в памяти. Пока процесс завершается, ответ 503. Образ проверяет готовность командой `engmark ready`.
- `GET /api/v1/cards?limit=1000` отдаёт колоду по умолчанию: `items`, `total`, `limit`, `offset`. `limit` от 1 до 1000, по умолчанию 50. Ответ несёт слабый `ETag` (SHA-256 тела JSON) и `Cache-Control: public, max-age=0, must-revalidate`. Повтор с тем же `If-None-Match` — 304. Выбранная колода: `GET /api/v1/decks/{id}/cards`.

Список карточек читается из снимка в памяти. Снимок содержит только активные карточки: архивные ученики не видят. Он пересобирается после каждой записи из админки (ревизия колоды растёт, `ETag` меняется) и при старте. Ответы `/api/v1/cards` несут заголовок `X-Deck-Revision` с ревизией колоды, с которой собран снимок. Ошибка имеет вид `{"error":{"code","message","details"?},"request_id"}`. Поле `details` необязательное: оно есть у ошибок админки (конфликты, проверка).

## Каталог

Источник правды — Postgres. Слова правятся в админке (`/admin`), `data/cards.json` нужен только для первого наполнения пустой базы: при старте он загружается, если у колоды `revision = 0`, и становится ревизией r1 (`source=seed`, автор `system`). Дальше файл игнорируется, и править его, чтобы поменять слова на сайте, бесполезно. Чтобы положить актуальные слова в git для ревью, есть `make export-cards` (а `make export-cards rev=42` сохранит колоду на ревизию r42). Тот же файл скачивается кнопкой «Экспорт» в админке. Цель называется не `export`: это слово занято директивой самого `make`.

Ключ активной карточки: колода, слово в нижнем регистре, `pos` и перевод. Два активных экземпляра одного ключа невозможны, архивная карточка заведению такой же заново не мешает. `pos` — одно из `verb`, `noun`, `adj`, `adv`. Слово состоит из английских букв, апострофа, дефиса и одиночных пробелов внутри.

Карточки не удаляются: «удаление» это архив (`archived_at`). Поэтому `id` стабилен и прогресс учеников в браузере не ломается.

### Ревизии и версии

Правки собираются в пакет (changeset): `create`, `update`, `archive`, `restore` и `imports` (загрузка JSON). Пакет применяется в одной транзакции и создаёт ровно одну ревизию колоды (r42 → r43). У каждой затронутой карточки версия растёт на единицу (v2 → v3), а её полный снимок сохраняется в `card_versions`: оттуда берутся история, экспорт на любую ревизию, база для слияния и откат.

Блокировки оптимистичные. Пакет несёт ревизию, от которой построен (`If-Match: "r42"`), и по каждой карточке ожидаемую версию. Если колода ушла вперёд, сервер ничего не пишет и отвечает 412 `revision_mismatch`. Если не совпала версия карточки, это 409 `version_mismatch`.

`make migrate-create`, `make migrate-up` и `make migrate-down` по-прежнему гоняют CLI миграций на базу разработки.

## Схема базы

Схема лежит в одной миграции `backend/migrations/000001_init.up.sql`: `decks` (с `revision`), `deck_revisions`, `cards` (с `version` и `archived_at`), `card_versions` и `admin_sessions`.

Пока на сервере нет живых данных, миграция переписывается целиком, новых файлов не добавляем. Поэтому после изменения `000001_init` базу нужно пересоздать. **Когда в базе появятся настоящие слова, это правило перестаёт действовать:** дальше только новые миграции `000002_…` и далее. Перед каждым обновлением сервера делайте `make host-backup` (см. «Резервная копия»).

Локально:

```sh
make env-down && rm -rf out/pgdata && make dev
```

На сервере:

```sh
docker compose --env-file .env -f docker-compose.yaml -p engmark-prod --profile host down -v && make host-up
```

`down -v` удаляет базу целиком. Если при старте в логе есть `database schema is from another build`, база создана другой сборкой: пересоздайте её этими командами.

## Экран занятий

`make dev` запускает экран вместе с API. Ctrl+C останавливает оба. Чтобы поднять только экран, когда API уже слушает:

```sh
make web
```

Откройте http://localhost:5173. Слова приходят одним `GET /api/v1/cards?limit=1000`. Если колода больше, загрузка продолжается со следующего `offset`. Следующее слово — случайная карточка, которая ещё не была в этом проходе. После последней карточки колода перемешивается снова.

Место запоминается в `ew-progress` (`index`, `order`, `wordsLen`), тема — в `ew-theme`: `dark`, `light`, `sepia`, `alt-dark`. Если набор id изменился, сохранённый порядок сверяется с каталогом: пропавшие id убираются, новые встают среди ещё не показанных. Повреждённая запись перемешивает колоду заново.

Пробел, стрелка вправо и `J` идут вперёд. Стрелка влево и `K` — назад. Озвучка идёт через синтез речи браузера. Шрифты лежат в сборке как woff2: Manrope, Fraunces, Space Grotesk, Syne и IBM Plex Mono. Темы `alt-*` подгружают свой набор отдельно.

## Сервер

Сервер — один Docker-стек. Caddy отдаёт экран и проксирует API на том же хосте, сжимает ответы (zstd и gzip) и ставит заголовки безопасности. HSTS начинается с `max-age=300`. Postgres слушает только сеть Docker. Процесс Go говорит по HTTP внутри этой сети. Caddy включает TLS, когда `ENGMARK_SITE` — доменное имя.

Поставьте Docker и откройте порты 80 и 443. Скопируйте туда тот же пример и поправьте `.env`. В репозиторий его не кладут.

```sh
cp .env.example .env
```

Замените `POSTGRES_PASSWORD` и поставьте тот же пароль в `DATABASE_URL`. Направьте DNS на машину и задайте:

```
ENGMARK_SITE=words.example.com
```

Для машины без домена оставьте `ENGMARK_SITE=:80`. `DATABASE_URL` в `.env` — адрес ноутбука, порт 5433. `make host-up` направляет API на Postgres внутри Docker-сети. Чтобы API ходил в другую базу, задайте `ENGMARK_DATABASE_URL` полным URL `postgres://`, включая `sslmode` и при необходимости `sslrootcert`.

```sh
make host-up
```

Откройте сайт. Страница и API на одном хосте. Там же `GET /healthz` и `GET /readyz`. Логи:

```sh
docker compose --env-file .env -f docker-compose.yaml -p engmark-prod --profile host logs -f app
```

`make host-down` останавливает серверные контейнеры и сохраняет том базы. Эта команда удаляет серверный том вместе с базой:

```sh
docker compose --env-file .env -f docker-compose.yaml -p engmark-prod --profile host down -v
```

Каждый старт сервера применяет встроенные миграции. Файл `/data/cards.json` в образе используется только на пустой колоде (рабочий каталог процесса — `/`). Образ distroless, процесс без root. Слова на сервере живут в базе и правятся в админке, а `id` карточек не меняются, поэтому прогресс в браузере переживает выкладку.

Браузер вызывает `/api/v1/cards` на хосте сайта.

### Резервная копия

В базе живые слова, и из `data/cards.json` их уже не восстановить. Перед каждым обновлением сервера снимайте дамп:

```sh
make host-backup          # печатает имя файла, например engmark-20261015-120000.dump
```

Восстановить дамп в базу серверного стека (существующие таблицы заменяются):

```sh
docker compose --env-file .env -f docker-compose.yaml -p engmark-prod --profile host exec -T postgres \
  sh -c 'pg_restore --clean --if-exists -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < engmark-20261015-120000.dump
```

Храните дампы вне сервера. `make db-backup` делает то же для локальной базы разработки (`engmark-backup.dump`). `make dist-src` собирает zip исходников текущего коммита в `engmark-src.zip`.

### Первая выкладка админки

Схема базы в этой версии новая (одна миграция `000001_init`), поэтому старую базу на сервере нужно пересоздать. Это стирает всё, что в ней было; прогресс учеников живёт в браузерах и не пострадает, потому что `id` карточек из `data/cards.json` те же.

1. Обновите код на сервере и на всякий случай снимите дамп старой базы: `make host-backup` (пока стек ещё работает на старой версии).
2. Пересоздайте базу:

   ```sh
   docker compose --env-file .env -f docker-compose.yaml -p engmark-prod --profile host down -v
   ```

3. Сгенерируйте хеш пароля (на любой машине с Go: `make admin-hash`) и впишите в `.env` на сервере:

   ```
   ADMIN_PASSWORD_HASH=...
   ADMIN_COOKIE_SECURE=true
   ADMIN_ALLOWED_ORIGINS=
   ```

   На сайте с доменом и https `ADMIN_COOKIE_SECURE` должен быть `true` (в `.env.example` стоит `false` для ноутбука). `ADMIN_ALLOWED_ORIGINS` на сервере пустой: свой адрес разрешён и так. Если сайт без домена (`ENGMARK_SITE=:80`, обычный http), поставьте `ADMIN_COOKIE_SECURE=false`, иначе браузер не сохранит вход, и помните, что пароль тогда идёт открытым текстом.
4. Поднимите стек:

   ```sh
   make host-up
   ```

5. Проверьте:
   - в логе `app` (`docker compose --env-file .env -f docker-compose.yaml -p engmark-prod --profile host logs app`) есть `seeded the admin deck from the cards file` с `"cards":375` и `admin API enabled`;
   - откройте `https://ваш-домен/admin`, войдите: в боковой панели «Слова 375» и «Ревизия на сервере r1», в «Истории ревизий» одна ревизия «Начальная загрузка из data/cards.json», автор «система», `+375`;
   - экран занятий на `/` показывает слова;
   - `make host-down && make host-up`: в логе `cards file ignored: the deck already has revisions`, ревизия осталась r1.
6. С этого момента база живая: новые изменения схемы только новыми миграциями `000002_…`, перед каждым обновлением `make host-backup`.

## Админка

`/admin` — редактор колоды для одного админа. Как устроена работа:

- **Вход** по паролю, хеш которого лежит в `.env` (см. «Админка: вход»). Если сессия кончилась в разгар работы, вход открывается поверх экрана, ничего не теряется.
- **Черновик.** Правки, новые слова, архив, возврат из архива и загруженные JSON-файлы копятся в черновике браузера (`localStorage`) и переживают перезагрузку. На сервер ничего не уходит, пока не нажата «Сохранить изменения».
- **Ревизии.** Сохранение записывает весь черновик одной транзакцией и создаёт одну ревизию колоды (r42 → r43). У каждой затронутой карточки растёт версия (v2 → v3), снимок версии хранится.
- **Конфликты.** Если колоду кто-то изменил после начала правки, сервер ничего не пишет. Админка сливает изменения сама и спрашивает только про поля, которые меняли обе стороны.
- **Импорт.** JSON в формате `data/cards.json` проверяется в браузере и на сервере, дубли пропускаются, строки с ошибками не попадают в черновик.
- **История.** Лента ревизий, карточки каждой ревизии, версии карточки, экспорт любой ревизии в файл и откат к ревизии через обычный черновик.

Подробности: «Админка: вход», «API админки», «Админка: данные на клиенте», «Админка: экран слов» (там же загрузка JSON, сохранение и конфликты, история ревизий).

## Админка: вход

Админка — отдельная страница `/admin` и API `/api/v1/admin/*`. Доступ у одного админа. Пока `ADMIN_PASSWORD_HASH` не задан, админ-API выключено: все `/api/v1/admin/*` отвечают 404, а в логе при старте есть предупреждение.

1. Сгенерируйте хеш пароля (от 8 до 72 символов). Команда спросит пароль без эха и напечатает значение для `.env`:

   ```sh
   make admin-hash
   ```

   Это bcrypt-хеш, упакованный в base64: в нём нет символа `$`, который `make` и docker compose считают подстановкой переменной. Обычный bcrypt (`$2a$…`) тоже подойдёт, напечатать его можно командой `engmark hash-password --raw`.

2. Впишите результат в `.env`:

   ```
   ADMIN_PASSWORD_HASH=...
   ```

3. Остальные переменные:

   | Переменная | По умолчанию | Смысл |
   | --- | --- | --- |
   | `ADMIN_SESSION_TTL` | `12h` | срок сессии, при активной работе продлевается |
   | `ADMIN_COOKIE_SECURE` | `true` | флаг `Secure` у cookie. На ноутбуке по `http` поставьте `false`, на сервере с https оставьте `true` |
   | `ADMIN_ALLOWED_ORIGINS` | свой хост | список Origin через запятую, которым можно писать. Для `vite dev` — `http://localhost:5173` |
   | `ADMIN_TRUSTED_PROXIES` | пусто, в compose частные сети | прокси, которым верим в `X-Forwarded-For` (для лимита попыток входа) |

Страница админки собирается как вторая точка входа Vite (`frontend/admin.html`, код в `frontend/src/admin`), Go отдаёт её на `/admin` и любые вложенные пути. В ней нет inline-скриптов: CSP в Caddyfile разрешает только хеш скрипта темы из `index.html`. Для `/admin*` и `/api/v1/admin*` Caddy добавляет `X-Robots-Tag: noindex, nofollow`; в Caddyfile есть закомментированный `basic_auth` как второй рубеж.

Сессия лежит в cookie `em_admin`: `HttpOnly`, `SameSite=Strict`, путь `/api/v1/admin`. В базе хранится только sha256 токена. Запросы на запись проверяются по заголовку `Origin` (или `Sec-Fetch-Site: same-origin`), иначе 403 `forbidden_origin`. Вход ограничен пятью попытками в минуту на IP и общим лимитом; неверный пароль и превышение лимита выглядят для пользователя одинаково, ответ занимает не меньше 0,3 с. Истёкшие сессии удаляются раз в час.

## API админки

Все пути начинаются с `/api/v1/admin`, ответы с `Cache-Control: no-store`, ETag сильные (`"r42"` у колоды, `"v3"` у карточки). Запись без cookie-сессии — 401.

| Метод и путь | Что делает |
| --- | --- |
| `POST /session` `{password}`, `GET /session`, `DELETE /session` | вход, проверка, выход |
| `GET /deck` | `{id, slug, title, revision, activeCards, archivedCards}`, `If-None-Match` → 304 |
| `GET /cards?q=&pos=&state=active\|archived\|incomplete&limit=&offset=` | список для таблицы |
| `GET /cards/{id}`, `/cards/{id}/versions`, `/cards/{id}/versions/{v}` | карточка и её история |
| `GET /changes?since=42` | карточки, изменённые после r42: текущие и как были на r42 (основа слияния) |
| `POST /changesets/validate` | пробный прогон без записи (предпросмотр импорта) |
| `POST /changesets` | применить пакет, обязателен `If-Match: "r42"` |
| `GET /revisions`, `/revisions/{rev}` | лента ревизий и состав ревизии |
| `GET /revisions/{rev}/export`, `GET /export` | колода в формате `cards.json` на ревизию или сейчас |
| `POST /revisions/{rev}/revert-draft` | пакет, который вернёт колоду к r{rev}. Сам ничего не пишет |

Коды ошибок записи: 400 `invalid_argument`, `empty_changeset`, `no_changes` (с `details.errors`), 401 `unauthenticated`, 403 `forbidden_origin`, 409 `version_mismatch`, `duplicate_card`, 412 `revision_mismatch` (`details`: `baseRevision`, `currentRevision`), 413 `payload_too_large` (тело больше 4 МБ у changeset и 32 КБ у остальных), 428 `precondition_required` (нет `If-Match`).

Пример записи (вход один раз, дальше cookie из файла):

```sh
curl -c jar -H 'Origin: http://localhost:5050' -H 'Content-Type: application/json' \
  -d '{"password":"…"}' http://localhost:5050/api/v1/admin/session

curl -b jar -i -H 'Origin: http://localhost:5050' -H 'Content-Type: application/json' \
  -H 'If-Match: "r1"' \
  -d '{"baseRevision":1,"message":"Новое слово","create":[{"word":"luggage","pos":"noun","translation":"багаж"}]}' \
  http://localhost:5050/api/v1/admin/changesets
```

Одну и ту же карточку нельзя указывать в двух разделах changeset (ошибка `duplicate_id`). Единственное исключение — пара `update` и `restore` с одинаковой `baseVersion`: это «вернуть из архива с правками», версия растёт на единицу.

### Загрузка слов из JSON

Кнопка «Загрузить JSON» в шапке открывает окно. Файл — массив карточек в формате `data/cards.json`: обязательны `word`, `pos`, `translation`, остальные поля можно не писать. Лишние поля отбрасываются, пробелы по краям обрезаются. Файл читается в браузере (перетащите его в окно или выберите; кнопка «Использовать пример файла» берёт `src/admin/fixtures/travel-words.json`), на сервер до сохранения черновика он не уходит.

Проверка идёт в три слоя:

1. **В браузере**: размер (до 4 МБ, проверяется до чтения файла), JSON, массив ли это, не пустой ли он, не больше ли 5000 строк, правила полей (те же, что в редакторе), повторы внутри файла, совпадения с колодой и с черновиком. Колоду окно берёт из `GET /export` при открытии. Карточка, которую черновик отправляет в архив или переименовывает, дублем не считается: при сохранении её ключ освободится раньше, чем добавится файл.
2. **На сервере**: окно отправляет в `POST /changesets/validate` только этот файл и только строки, прошедшие первый слой. Если колода успела измениться, сервер найдёт новые дубли, и счётчики обновятся (в окне это видно строкой «колода изменилась, сервер нашёл дублей ещё: N»).
3. **Если сервер не ответил**, остаётся результат браузера с пометкой «проверено локально». Добавить в черновик всё равно можно: полная проверка повторится при сохранении.

В окне три счётчика (будут добавлены / уже есть — пропуск / с ошибками). Ошибки показываются списком (номер строки в файле, слово, причина), первые 100, дальше «…и ещё N». Дубли свёрнуты в раскрывающийся список с пометкой, где найден дубль: в колоде, в черновике или повтор в файле. «Скачать отчёт об ошибках» отдаёт `<имя файла>-errors.json` со всеми ошибками и пропусками (`index` с нуля, `row` с единицы, слово, причины).

«Добавить N в черновик» кладёт в черновик только годные строки. В таблице появляется строка «Из файла · travel-words.json · N новых слов» с кнопкой «Убрать»; она видна в «Активных» и «В черновике», когда нет поиска и фильтра по части речи. Если файл с таким именем уже в черновике, окно предупреждает: повторные карточки будут пропущены как дубли.

Для разработки без бэкенда: `fakeApi` умеет `exportCurrent` и `validate` (только раздел `imports`), поэтому окно можно пробовать на поддельном сервере.

### Сохранение и конфликты

«Просмотреть» и «Сохранить изменения» в панели черновика открывают одно и то же окно: список всего, что будет записано (тип, слово, перевод, `v2 → v3` или «новая · v1», файлы), поле «Комментарий к ревизии» и строка `r42 → r43 · +8 ~1 −0` (добавлено, изменено, в архив). Если комментарий оставить как есть, сервер запишет его в историю; если стереть, подпишет ревизию сам. «Сохранить» отправляет `POST /changesets` с `If-Match: "r<основа>"`. Пока запрос в пути, окно нельзя закрыть и нажать ещё раз.

Что происходит дальше, по ответу сервера:

| Ответ | Что видит человек | Что с черновиком |
| --- | --- | --- |
| 201 | «Сохранено как r43. Каталог для учеников обновлён». Таблица и ревизия перечитываются; открытая новая карточка получает настоящий id | очищается |
| 412 `revision_mismatch`, 409 `version_mismatch` | окно «Колода изменилась, пока вы работали»: «Вы начали с ревизии r42, на сервере уже r43. Ничего не записано». Выбирать нужно только там, где правили и вы, и сервер: у каждой такой карточки таблица «Поле / Ваш вариант / На сервере · vN» (под полем «было: …»). Поля, которые вы не трогали, подтягиваются сами, они перечислены строкой «Автоматически с сервера». Отдельное решение просят конфликты уровня карточки: её отправили в архив на сервере, а вы правили; вы отправили в архив, а на сервере правили; ваше новое слово уже добавили на сервере | остаётся. «Применить поверх r43» переносит его на новую основу и сразу повторяет сохранение; если за это время сервер ушёл вперёд снова, окно появится ещё раз. «Позже» ничего не меняет: панель черновика подпишет «нужно обновить основу». Если после слияния ваших правок уже нет (сервер уже содержит всё то же), сообщение «сохранять нечего» |
| 409 `duplicate_card`, 400 | плашка «Сервер не принял изменения. Ничего не записано» с причиной у каждой карточки; строки в таблице отмечены красным и меткой «Не принято», первая карточка открывается в редакторе. Ошибки в строке файла показывает само окно сохранения («Строка 2. Слово: …») | остаётся целиком. Метка пропадает, когда карточку изменили |
| 401 | слой «Сессия закончилась» поверх; окно сохранения остаётся под ним с тем же комментарием, после входа в нём написано «Вы снова вошли, черновик на месте», остаётся нажать «Сохранить» | остаётся |
| нет связи, 5xx | «Не удалось сохранить, черновик на месте» и кнопка «Повторить» | остаётся |

**Потерянный ответ.** При сетевой ошибке и 5xx запись могла дойти до сервера, а ответ нет. Прежде чем показать «не удалось», клиент читает `GET /deck` и ревизию `base + 1` из `GET /revisions`. Если колода не сдвинулась, запись не прошла, и «Повторить» безопасен. Если ревизия `base + 1` есть и совпадает с отправленным (основа, автор, источник, комментарий, число созданных, изменённых, архивных, возвращённых карточек и файлы), клиент считает сохранение удавшимся и пишет об этом в сообщении («Ответ сервера потерялся по дороге, но запись нашлась в истории»). Если колода ушла вперёд и ревизия чужая, это обычный конфликт. Если проверить не удалось, остаётся «Повторить»: двойную запись не даст `If-Match`.

Ограничение проверки: две правки с одной основой, одинаковым комментарием и одинаковыми счётчиками от разных людей она отличить не может. Практически это безопасно: такая запись содержит то же самое, что человек хотел сохранить. Идентификаторы созданных карточек при потере ответа неизвестны, поэтому открытый редактор новой карточки закрывается.

### История ревизий

Раздел «История ревизий» в боковой панели — лента от новой ревизии к первой. У каждой: номер, заголовок (комментарий, а без него подпись по источнику: «Начальная загрузка из data/cards.json», «Импорт: a.json», «Правки карточек»), автор («Вы» или «система»), время, «основа rN» (у r1 — «первая ревизия»), метка «текущая» у самой новой, бирки `+N ~M −K` (добавлено вместе с возвращёнными из архива, изменено, в архив) и загруженные файлы с числом добавленных и пропущенных строк. Лента читается по 30 (`GET /revisions?limit=30&before=`), «Показать ещё» берёт следующие. Когда колода уходит вперёд, новые ревизии появляются сверху сами.

«Показать карточки» раскрывает ревизию (`GET /revisions/{rev}`): какие карточки в ней появились, изменились, ушли в архив или вернулись, первые 100 и «Показать ещё». Ссылка `vN` у карточки открывает её в редакторе сразу на вкладке «Версии» на этой версии.

**Экспорт.** Кнопка «Экспорт» у ревизии скачивает снимок колоды на ту ревизию (`GET /revisions/{rev}/export`) файлом `engmark-r42.json` в формате `data/cards.json`. Кнопка «Экспорт» в шапке раздела «Слова» скачивает текущую колоду (`GET /export`); номер в имени файла берётся из ответа сервера. Черновик в файл не входит.

**Откат.** «Откатить к rN» есть у всех ревизий, кроме текущей. В базе он ничего не меняет: сервер (`POST /revisions/{rev}/revert-draft`) строит changeset, который вернёт колоду к rN, а админка кладёт его в обычный черновик с подписью «Откат к rN» и показывает слова с фильтром «В черновике». Дальше всё как всегда: просмотреть, поправить, сохранить с `If-Match`; комментарий ревизии по умолчанию — «Откат к rN». Если в черновике уже есть правки, сначала спрашивается, отменить их или не откатывать; прежний черновик заменяется только после того, как новый собран. Основа для каждой карточки отката (её текущее состояние) берётся одним запросом `GET /changes?since=rN`; если два ответа сервера относятся к разным ревизиям, черновик не собирается и предлагается нажать ещё раз. Если колода уже совпадает с rN, откатывать нечего.

**Версии карточки.** В редакторе существующей карточки две вкладки: «Карточка» и «Версии» (стрелки переключают). «Версии» читает `GET /cards/{id}/versions`: v1…vN с ревизией и временем, у новой метка «текущая», у архивных «в архиве». Раскрытая версия показывает таблицу «Поле / vK / Сейчас · vN» только по отличающимся полям. «Взять значения из vK» кладёт её поля в форму (вкладка «Карточка», изменённые поля подсвечены), дальше обычная правка: «В черновик», затем сохранение. Несохранённый текст в форме при переходе между вкладками не теряется.

## Тесты

`make test` запускает `go test ./...` в `backend/` и требует Docker.

Во `frontend/`: `npm run lint`, `npm test`, `npm run build`, `npm run check:size`. `check:size` считает два бюджета gzip по манифесту Vite: экран занятий 80 КБ (чанки, достижимые из `index.html`) и админка 60 КБ (только её собственные чанки, без общих с экраном занятий). Экран занятий не должен импортировать ничего из `src/admin`: скрипт это проверяет.

Сквозные тесты Playwright (`npm run test:e2e`) идут против поднятого стека, по умолчанию `http://127.0.0.1` (другой адрес — `PLAYWRIGHT_BASE_URL`):

На страницах админки — axe (критичные и серьёзные нарушения).

Админский файл нуждается в пароле: `E2E_ADMIN_PASSWORD`, хеш которого стоит в `ADMIN_PASSWORD_HASH` у стека. Без переменной он пропускается. Тесты меняют колоду, но их можно гонять повторно на той же базе: последний откатывает её к состоянию до прогона. Локально по http нужен `ADMIN_COOKIE_SECURE=false`:

```sh
# в .env: ADMIN_PASSWORD_HASH (make admin-hash) и ADMIN_COOKIE_SECURE=false
make host-up
cd frontend && E2E_ADMIN_PASSWORD='ваш пароль' npm run test:e2e
```

Сервер пускает не больше пяти попыток входа в минуту с адреса: спек входит один раз и переиспользует сессию.

## CI

Push в `main` и pull request запускают четыре задачи. Секрет GitHub не нужен.

- API: `go vet`, staticcheck, govulncheck и `make test-race`.
- Фронтенд: `npm run lint`, `npm test`, `npm run build` и `npm run check:size`.
- Сборка образа без публикации в реестр.
- Playwright на Chromium против поднятого стека: экран занятий и админка. Пароль админа задача генерирует сама на каждый прогон (`openssl rand`, хеш через `engmark hash-password`), секрет GitHub не нужен. Если тесты упали, в лог выводится хвост лога `app`.

Dependabot раз в неделю проверяет Go-модули в `/backend`, npm в `/frontend`, GitHub Actions и Docker.
